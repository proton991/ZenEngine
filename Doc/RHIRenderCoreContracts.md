# RenderCore use of ZenRHI

The standalone binding and lifetime contracts are in [ZenRHI](../ZenRHI/include/ZenRHI/README.md). The engine applies the following policies when it prepares frames, records commands and retires resources.

## Invariant verification and native failures

Engine-owned C++ uses no `try`, `catch`, `throw`, or `LOG_ERROR_AND_THROW`. `VKCHECK` has been removed. Native calls either classify their result explicitly and reject the affected operation, or use a release-active verification when continuing would violate an invariant. Positive Vulkan statuses do not by themselves certify a usable output. The source-policy check is `python tools/check_no_exceptions.py` (also registered as the `NoEngineExceptions` CTest).

A device can set RHIDeviceDesc::messageCallback to receive diagnostics from any worker. Without a callback ZenRHI writes diagnostics to standard error. Applications may install a CPU-only fatal diagnostic with `SetVerificationReporter`. The interactive Windows scene demo uses a native message box for fatal startup/invariant errors and terminal frame failures; automated frame-limited and smoke runs keep diagnostics on stderr/logs. No failed renderer is needed to display the message.

## Validation defaults

The scene demo and editor preserve the build default unless `--enable-validation` or `--disable-validation` is supplied. Conflicting flags are rejected. The demo's `--validation-printf` also enables validation and cannot be combined with `--disable-validation`. Native correctness tests and validation smoke/capture scripts explicitly enable validation in every configuration; performance runners disable it unless their diagnostic opt-in is requested.

## Resources and recorded commands

Direct `IRHICommandContext` calls borrow layouts for the duration of the call and do not acquire resource ownership. Raw contexts retain bindings across calls; callers must keep bound resources alive through their last use or replace/discard those bindings before releasing them. `RHICommandList` retains each recorded resource, including a texture view's base texture, until reset, rollback or destruction. Callers must still protect every resource and dependency through GPU completion or definite discard; recorded-command retention is not GPU retirement. `Destroy*`/`ReleaseReference` releases a reference immediately and does not wait for GPU work. A submitted command list reset does not imply GPU completion. RenderCore's deferred retirement provides this protection for its managed resources; direct RHI callers must provide it themselves.

`RHITextureViewCreateInfo::arrayView` explicitly selects a 1D/2D array view with one layer, or a cube-array view with six layers; larger layer ranges retain their existing automatic array selection. Cube arrays require `imageCubeArray`, and 3D array views are rejected. RenderCore forwards this through `TextureViewFormat::arrayView`; callers need no extra image layer solely to obtain an array view.

## Acceleration structures

`RHIAccelerationStructureInstance` is a CPU description: a row-major 3x4 transform, 24-bit custom index, 8-bit mask, instance flags and a BLAS resource reference. It is not a native GPU byte layout. RDG recorders and RHI command lists copy geometry and instance arrays; command lists retain the referenced resources. Builds validate finite, invertible transforms, custom-index/flag ranges and retained BLAS membership. RenderCore omits scene instances with singular transforms, which cover no area, rather than failing the frame. Size queries use instance counts and permit unresolved BLAS references during allocation preflight. GPU-generated native instance bytes are not part of this contract.

Each backend encodes and owns its native instance upload through GPU completion. Vulkan packs `VkAccelerationStructureInstanceKHR` into host-coherent, device-addressable storage with a 16-byte-aligned address; queue submission makes those completed host writes available. Geometry buffers require AS-input usage, and scratch requires storage-buffer usage. RenderCore requests device-address usage only when the backend advertises it; Vulkan validates the resulting address-plus-offset alignment. AS-build input reads use shader-read access, while scratch uses AS-read/write access at the build stage. See the [Vulkan AS build synchronization contract](https://docs.vulkan.org/spec/latest/chapters/accelstructures.html).

RDG imports AS objects directly and tracks their contents, retained writers, versions and queue history by AS stable identity. Buffer state and access retain the `RDGBufferResourceState`, `GetBufferState`/`UpdateBufferState` and `DeclareBufferAccessForPass` APIs. Acceleration structures use distinct `RDGAccelerationStructureResourceState`, `GetAccelerationStructureState`/`UpdateAccelerationStructureState` and `DeclareAccelerationStructureAccessForPass` APIs, with separate state maps. Both paths share internal hazard, visibility and access-recording logic. A TLAS binding declares reads of both the TLAS and its retained BLASes. Builds use whole-AS memory barriers; scratch and geometry remain ordinary buffer resources. An in-place update preserves the destination's prior contents. Cross-queue query/build dependencies use the existing submission protocol, and Vulkan derives AS queue accessibility from its private storage allocation. Scene budgets include backend instance-upload bytes until the submission retires.

An update requires a previously recorded compatible build with update enabled. Index storage/ranges/counts and geometry formats/flags must remain compatible; index values and active primitive state must remain unchanged. The caller validates GPU input contents, retains the current scene snapshot, and must discard an AS recorded by failed/unsubmitted work. Build commands use the graphics context. Native validation failures enter the recording-error/submission-failure path. RenderCore publishes its snapshot after graph handoff and invalidates readiness when submission failure blocks the backend. Query descriptors require a TLAS and use ordinary bindings, separate from material bindless heaps.

## Vulkan queue sharing

RenderDevice owns `RenderSubmissionHistory`, which tracks exact writers/layout transitions and concurrent readers per physical resource. An overwrite depends on the relevant readers, and cross-graph consumers use exact accepted queue/serial points or pending batch-group references. History preparation is transactional. Frame history commits at CPU handoff and is confirmed by the batch result; standalone graphs commit after successful synchronous CPU processing. Failed queued work invalidates speculative history and blocks dependent work. RenderGraph/RDGExecutor consume supplied capabilities and producer provenance to plan dependencies and barriers; they never query native progress or submit work. Explicit external-state invalidation still requires the caller to arrange completion and visibility of external work.

`RHICommandContextType` is the common logical queue vocabulary. `RHIQueueCapabilities` is the authoritative snapshot for native queue equivalence and async dependency support. Equal native IDs allow shared barrier history, but each logical queue retains its own serial timeline. All graph submissions, including a single group, use the grouped executor path. `SubmitGroups` waits for native acceptance without ending the native frame. `SubmitQueuedGroups` returns a ticket for a non-presenting batch; RenderCore uses it for threaded uploads when timeline dependencies are available. Standalone graph callers without a retirement output retain synchronous acceptance.

Frame adapters own presentation and the successful frame boundary. A viewport passed to `SubmitFrame` or `SubmitGroups` is presented by the executor: when the last group runs on the graphics queue, the presentation copy joins that run's native submission as its own command buffer and submit info, so only the copy waits for the acquired image. The group's accepted point is its own command list's receipt, not the copy's or the context's latest serial. A frame whose last group runs on another queue presents in a separate submission. An asynchronously handed-off batch rejected later stops the renderer because its scheduled state may already have consumers. A synchronous `SubmitGroups` rejection before any work is accepted remains retryable, including with a viewport; RenderCore reports that presented frame as `eDeclined`. Partial acceptance and fatal failures still stop rendering.

RenderCore's `ResourceRetirement` combines required serials with every unresolved batch ticket that can use the resource. Frame and upload handoffs share an ordered pending list; handing off another batch does not drain older work. Each batch reports only the native serials it advances, including partial execution and presentation. A later ticket cannot replace earlier tickets because they can use different queues. Pool readiness is nonblocking; frame-slot reuse waits for the CPU results and required GPU serials. Resolving a ticket folds its serials into the requirement, while fatal/uncertain work remains protected. Staging blocks and retained upload destinations use the same retirement contract. Vulkan recording epochs and lifetime tracking remain backend-local.

## Global bindless heap

Shaders declare the heaps as runtime-sized arrays, so changing capacities needs no shader change. `RHIGPUInfo::bindlessHeapCapacities` reports the counts the backend actually created; use these counts for allocation and bounds checks, rather than the requested options. Later option changes do not resize a live heap. Shader/pipeline validation still checks the fitted heaps together with ordinary descriptors and color attachments, so a pipeline that needs more than the reserve is rejected on a device whose heaps were reduced to a limit. RenderCore places scene textures in 2D slots from zero and scene samplers after the fallback sampler in slot zero. A scene that does not fit makes `RenderScene` write an error message and abort before changing the scene or allocating its resources. The demo requests the 2D and sampler counts with `--bindless-textures=N` and `--bindless-samplers=N`.

## Uniform buffers and push constants

Recorded push-constant updates forward the requested byte offset to the backend. Data must be non-null and nonempty; Vulkan offsets and sizes must be multiples of four and fit the supplied pipeline's declared push-constant range with nonzero stage visibility. Invalid updates latch a recording error before `vkCmdPushConstants`; a null recorded payload is preserved for backend rejection without copying bytes. RenderCore V2's separate restriction to offset zero remains in place.

## Vulkan device and presentation requirements

`PrepareForPresent` requires the entire logical color backbuffer in color-attachment usage, read/write access, at color-attachment-output stage on the graphics queue. RenderDevice declares that final state before graph preparation. RDG schedules any required transition after all backbuffer accesses, including cross-queue dependencies; an already matching state adds no image barrier. Direct callers must establish the same state. The viewport uses explicit transfer and attachment stage/access masks and restores the logical backbuffer to that state after the copy.

Callers still provide image transitions for the selected subresources and retain the owning texture until recorded/GPU work completes. Direct views and layouts do not add an image ownership reference; recorded commands retain the base texture as described above. 3D-slice attachments are rejected. Dynamic rendering is the only rendering path, including explicit attachment views and layered attachments. RenderCore's existing RDG attachment and logical-view restrictions are unchanged; these new selection overloads are available to direct RHI callers.

## Vulkan command recording and pipeline compilation

`RHIGfxPipelineMultiSampleState::sampleMasks` is a 64-bit coverage mask: bit i enables sample i. It defaults to all samples enabled, including after changing `sampleCount`. Explicit zero or partial masks are preserved. Vulkan receives the low and high 32-bit words in sample order, and RenderCore pipeline keys include the full mask.

A device-owned `VkPipelineCache` retains native compilation data for graphics and compute pipeline creation until device destruction. It uses default internal synchronization and complements RenderCore's existing cache of complete pipeline objects. Cache creation failure falls back to `VK_NULL_HANDLE`. Cache data is not saved to disk; startup benefits and persistence/versioning policy require separate measurement. Renderer initialization warms the measured late-use compute keys `HybridTemporalSP`, `ResetDrawIndirectSP` and `VoxelPreDrawSP` through RenderDevice's existing cache. Missing programs are skipped and warmup failures retain ordinary cache failure handling. This moves compilation to initialization while keeping native creation on the RHI thread. Remaining first-entry GI compilation is covered by the proposed [asynchronous-compilation follow-up](../../../../Doc/RHIPipelineCompilationFollowup.md).

## Allocation, features and scalar contracts

Vulkan enables its required extension features and the supported optional core features (pipeline/sampler state and independent blend), with optional results in `RHIGPUInfo`. Tessellation is currently unsupported: its feature is disabled, its reported capability is false, and tessellation stages or patch-list pipelines are rejected before native creation. The RHI does not yet represent patch-control-point state. `imageCubeArray` and `fullDrawIndexUint32` are enabled when supported. `RHIGPUInfo::supportImageCubeArray`, `supportSamplerMirrorClampToEdge`, and `maxDrawIndexedIndexValue` expose the corresponding usable capabilities/limit. Mirror-clamp sampling requires the optional `VK_KHR_sampler_mirror_clamp_to_edge` extension. Anisotropy is clamped to the device limit. Unnormalized samplers must use matching filters, nearest mip filtering, zero LOD range, clamp addressing, and no comparison or anisotropy. Robust buffer access is off by default and can be requested through `RHIOptions::SetRobustBufferAccessEnabled`. The viewport prefers D32 depth, then D32 with stencil and D24 with stencil. Debug Printf is opt-in through `SetDebugPrintfEnabled` or the demo's `--validation-printf` flag.

## Recoverable creation and recording failures

Buffer, texture/view, shader, pipeline, sampler, viewport and command-context factories return null after cleaning partial native state. Callers must check before recording use. `RHICommandList::Create(nullptr)` also returns null. RenderCore does not cache failed pipelines and counts failures. The first failure of a pipeline key retries on the next request; each further consecutive failure defers that key's retries by a doubling number of frames, up to 256, so a persistent rejection is not recompiled every frame. A success clears the key's failure record. Staging and uniform growth reject allocation/mapping failure without publishing an unusable block. Backend initialization and broken ownership invariants retain an explicit fatal path.

## RHI worker shutdown

Worker jobs report failure explicitly through `Fail(RHIError)`. There is no exception containment or propagation in engine code. `DispatchChecked` distinguishes accepted, queue-full, lifecycle-closed and failed admission. Failure wakes blocked producers and cancels unstarted normal jobs. `InvokeChecked` completes an accepted execution or cancellation exactly once; admission rejection completes directly without waiting for a job that was never queued. Batch cancellation preserves the original terminal cause and signals its ticket; frame timing completes with an error. Cleanup drains in FIFO order, bypasses queue capacity during shutdown, and runs before the backend finalizer. Foreign exceptions crossing a worker's `noexcept` boundary terminate; they are not a supported error-recovery mechanism.

## GPU budgets and device-loss diagnostics

`GetGPUMemoryStats()` retains allocator commitment/peak counters. If `VK_EXT_memory_budget` is enabled, `budgetAvailable`, `heapCount` and `heaps` also expose each heap's size, driver-estimated usage, budget and device-local flag. Driver estimates can include allocations outside VMA and are not reservations. At a frame boundary, when any device-local heap reaches 90% of its nonzero budget, RenderCore retires the cached graph resources that the newest pooled build did not use. That build's working set stays pooled, so sustained pressure does not rebuild the same targets every frame. Active/exported resources remain owned; retired resources still wait for their serials. VMA allocations request the within-budget policy. Optional allocation requests may fail locally with null/status and permit a caller-selected fallback. R17 originally used **option B** for all required frame work. Production fix Phase 1 preserves blocking after asynchronous handoff or partial acceptance, and permits retry after a synchronous rejection that accepted no work. All accepted GPU ownership remains protected through cleanup. Unsubmitted operations may be retried after explicit discard; there is no implicit replay or automatic device recreation. No destructive eviction of active scene resources or forced device-idle wait is introduced. Without the extension, budget policy is unavailable and existing allocation-error handling remains active.

Device loss emits the operation and device identity once and blocks submissions. Set `RHIOptions::SetDeviceLossDiagnostics(true)` before backend initialization, or run the demo with `--device-loss-diagnostics`, to enable pass breadcrumbs and optional `VK_EXT_device_fault` reporting. Supported AMD devices use buffer markers. Other devices use buffer fills that wait for all earlier work, so a marker means everything recorded before it finished; later work does not wait for a fill, so pass boundaries are not serialized. Each native command buffer keeps at most 1024 labeled scopes, with separate start/end markers and its queue identity. Reporting uses fixed-capacity fault storage and prints truncation through the Vulkan result.

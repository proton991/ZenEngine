## Phase 1 implementation

- Presented frames and renderer dispatch return `RenderFrameResult`: submitted, declined, failed or blocked. Standalone graph execution remains boolean.
- RDG distinguishes a retryable submission rejection from a recording/declaration error with `eSubmissionRejected`, without parsing diagnostic text.
- Inline frames use synchronous submission (also for multiple queues). Threaded handoffs keep their ticket and late-rejection blocking semantics. The RHI executor no longer treats a viewport alone as proof of asynchronous publication: a synchronous batch rejected before acceptance can retry. Partial acceptance still blocks.
- `PrepareFrame` polls ready tickets and handles recreation before scene updates. Presentation-backed views refresh their attachments after recreation. A late recreation still declines at handoff without committing the graph.
- Renderer notifications preserve committed histories on decline and re-request unsubmitted work. Newly allocated Hybrid history and previous-radiance initialization is repeated until accepted. Hybrid settings/provider history commits only on submission, and temporary history invalidation is restored after decline; storage invalidation from scene/size changes remains necessary.
- Editor policy continues after a decline or recording failure, and stops on a blocked device or the ninth consecutive decline. The demo continues only after a submitted or declined frame, with the same decline limit.
- Debug-only `ZEN_FORCE_VIEWPORT_RECREATION_INTERVAL=N` requests a recreation after each N submitted frames without changing the window size. Zero/unset disables it. `ResizeViewport` honors that explicit request even when the backend has not reported a size or surface change.

## Phase 3 implementation and design decision

Selected **3b, separate queued non-presenting batches**. Uploads also execute outside a presented frame (texture loading, standalone graphs and staging pressure). The RHI executor already owns detached commands and resource references through GPU completion and accepts ordered external submission points. Extending that existing batch path avoids adding an unsubmitted upload buffer to each frame and preserves standalone use. Folding uploads into a presented frame would need an additional standalone path and delay uploads until a frame exists.

- `SubmitQueuedGroups` uses the ordered worker without presenting or advancing the native frame. Threaded uploads use it only with asynchronous submission dependencies; `SubmitGroups` and the separate-transfer CPU completion fallback remain synchronous on other backends. Standalone graphs without a retirement output still wait for native acceptance.
- Each batch reports only serials advanced during its own worker execution, including partial submission and a presentation copy. Capturing the before/after serials on that worker avoids a render-thread drain and includes native work that can be flushed along with a group. Staging no longer diffs global render-thread serial snapshots.
- RenderDevice holds an ordered list of pending frame and upload tickets. Ordinary standalone execution and another handoff poll ready results without draining that list. `ResourceRetirement` retains all outstanding tickets, deduplicates merged requirements, and combines their individual serials as results arrive. A later ticket may cover a different queue and cannot replace earlier tickets.
- Staging blocks and retained destinations use these retirement requirements. Pool pressure and frame-slot reuse may still wait; ordinary upload handoff does not. Fatal or uncertain work remains protected, including during upload-queue destruction, until device teardown.
- Destroying a buffer or texture no longer flushes uploads. The pending upload's destination reference survives owner retirement and the later copy.
- A rejection before queued handoff or from synchronous submission retains payload bytes for retry. Rejection after asynchronous handoff is terminal, as for existing frame handoffs: dependent state may already be published. The worker cancels later batches, RenderCore clears speculative history, and extractions do not publish. Device-loss recovery remains deferred.

New gated tests cover frame N+1 plus `UpdateBuffer` while frame N's native submission is held, on shared and separate transfer queues. Both frame-poll and synchronous-submit wait counters stay unchanged, matching the no-upload gated frame test (zero added wait). The test verifies pending frame/upload ticket count, GPU dependency ordering, copied bytes, and CPU-versus-GPU retirement. Other tests cover destroying both upload destination kinds without flushing, two queued staging users on different queues, exact per-batch serials, no native frame advance for non-presenting work, late rejection with a queued consumer, partial acceptance, and retry plus CPU completion on a backend without timeline dependencies.

The gated tests prewarm staging storage and recording contexts. Cold native resource/context creation is still a synchronous RHI service; this phase removes submission drains, not that allocation cost. The failure test initially hit this first-use context creation; warming it before the gate isolated the intended queue/failure contract. Existing single-pending-frame tests were changed to exercise multiple handoffs, while the late-recreation test now explicitly makes the earlier result ready during recording.

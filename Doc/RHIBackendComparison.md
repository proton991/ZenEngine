# ZenRHI Vulkan backend references

Use NVRHI to compare what a standalone graphics library asks of its caller. Use UE5 to compare how a renderer hands work to the RHI, and how its Vulkan backend submits and retires that work. Leonida shows how a guest graphics API translates to Vulkan and how to test the resulting behavior on a real driver.

## Implementation comparison

### Who records and submits?

ZenEngine’s default path records engine commands in RenderCore and hands them to one ordered RHI worker for native translation and submission. NVRHI opens a native Vulkan command buffer on the thread recording each list. Calling `executeCommandLists` submits the closed lists to the selected queue, whose submission path takes a mutex. Independent lists can therefore record in parallel without requiring the host to adopt an RHI worker. [Zen worker](../ZenRHI/src/Core/RHIThread.cpp#L131) · [NVRHI recording](https://github.com/NVIDIA-RTX/NVRHI/blob/bf0bbd9b666a7297492beb1999a4ddc0dfded143/src/vulkan/vulkan-commandlist.cpp#L69) · [NVRHI execution](https://github.com/NVIDIA-RTX/NVRHI/blob/bf0bbd9b666a7297492beb1999a4ddc0dfded143/src/vulkan/vulkan-device.cpp#L665) · [Queue submission](https://github.com/NVIDIA-RTX/NVRHI/blob/bf0bbd9b666a7297492beb1999a4ddc0dfded143/src/vulkan/vulkan-queue.cpp#L122)

UE5 is the closer comparison for scaling ZenEngine’s existing design. Where the backend and configuration allow it, the executor schedules translation jobs. Vulkan finalizes their contexts into platform command lists, enqueues their payloads, and processes queue submission. In ZenApp, measure main-thread recording, worker translation, and native submission separately. Parallel translation can address the second cost. [UE translation scheduling](https://github.com/EpicGames/UnrealEngine/blob/821fa3e7e3e5c66ddcd2d66d0603704f52e09fcc/Engine/Source/Runtime/RHI/Private/RHICommandList.cpp#L1568) · [Vulkan context finalization](https://github.com/EpicGames/UnrealEngine/blob/821fa3e7e3e5c66ddcd2d66d0603704f52e09fcc/Engine/Source/Runtime/VulkanRHI/Private/VulkanSubmission.cpp#L241) · [Submission handoff](https://github.com/EpicGames/UnrealEngine/blob/821fa3e7e3e5c66ddcd2d66d0603704f52e09fcc/Engine/Source/Runtime/VulkanRHI/Private/VulkanSubmission.cpp#L553) · [Epic’s threading overview](https://dev.epicgames.com/documentation/en-us/unreal-engine/parallel-rendering-overview-for-unreal-engine)

### When is a resource safe to reuse?

NVRHI’s tracked command buffers retain resource references and release them during collection after their queue submission completes. With mutable descriptor tables, the caller owns the referenced resources and synchronizes table writes. ZenRHI’s bindless registrations retain their owners and defer slot reuse until earlier recordings and submissions retire. Preserve that guarantee for existing callers. [NVRHI collection](https://github.com/NVIDIA-RTX/NVRHI/blob/bf0bbd9b666a7297492beb1999a4ddc0dfded143/src/vulkan/vulkan-queue.cpp#L339) · [Descriptor table contract](https://github.com/NVIDIA-RTX/NVRHI/blob/bf0bbd9b666a7297492beb1999a4ddc0dfded143/doc/ProgrammingGuide.md#L120) · [Zen lifetime tracker](../ZenRHI/src/Vulkan/VulkanLifetimeTracker.cpp#L18) · [Zen bindless retirement](../ZenRHI/src/Vulkan/VulkanDescriptorPool.cpp#L1640)

UE5’s normal deferred-deletion path can first hold entries for a configurable number of frames, then enqueue destruction behind GPU completion points on each queue. Leonida retires a contiguous prefix of device-wide submission tickets. In ZenRHI the tracked entry identifies the queues that used it, allowing unrelated queues to progress independently. [UE deferred deletion](https://github.com/EpicGames/UnrealEngine/blob/821fa3e7e3e5c66ddcd2d66d0603704f52e09fcc/Engine/Source/Runtime/VulkanRHI/Private/VulkanMemory.cpp#L4713) · [UE end-of-pipe task](https://github.com/EpicGames/UnrealEngine/blob/821fa3e7e3e5c66ddcd2d66d0603704f52e09fcc/Engine/Source/Runtime/VulkanRHI/Private/VulkanSubmission.cpp#L566) · [Leonida retirement](https://github.com/ItsNotRexed/Leonida/blob/98fa503f8a19c3ed65df1f4f2f0e4571aa42c4f7/runtime/src/retire_tickets.h#L8)

Submission failure is a concrete limit on adopting NVRHI’s queue interface. At this revision its Vulkan submit path allocates an ID before the native call, catches device loss, reports it by callback, and still returns the ID. ZenRHI callers use a published serial as evidence of native acceptance. Preserve ZenRHI’s fatal result on device loss and its existing regression test when evaluating a queue refactor. [NVRHI submit](https://github.com/NVIDIA-RTX/NVRHI/blob/bf0bbd9b666a7297492beb1999a4ddc0dfded143/src/vulkan/vulkan-queue.cpp#L139) · [Zen submit result](../ZenRHI/src/Vulkan/VulkanQueue.cpp#L590) · [Zen device-loss test](../ZenRHI/tests/VulkanQueueIntegrationTests.cpp#L512)

### Who decides resource transitions?

NVRHI offers optional automatic tracking at command-list scope and emits accumulated buffer and image barriers with synchronization2. UE5 compiles pass barriers in its render graph. On its parallel-rendering Vulkan path, a cross-queue transition can emit a release barrier, signal a semaphore, wait on the receiving queue, then emit the acquire barrier. Leonida also tracks layouts to implement D3D12 promotion and decay. For ZenRHI, UE5 is the useful reference for the graph/backend boundary and NVRHI for native barrier emission. ZenEngine already tracks cross-graph accesses and accepted queue dependencies in RenderCore. [NVRHI barriers](https://github.com/NVIDIA-RTX/NVRHI/blob/bf0bbd9b666a7297492beb1999a4ddc0dfded143/src/vulkan/vulkan-state-tracking.cpp#L214) · [UE graph compiler](https://github.com/EpicGames/UnrealEngine/blob/821fa3e7e3e5c66ddcd2d66d0603704f52e09fcc/Engine/Source/Runtime/RenderCore/Private/RenderGraphBuilder.cpp#L3859) · [UE transition processing](https://github.com/EpicGames/UnrealEngine/blob/821fa3e7e3e5c66ddcd2d66d0603704f52e09fcc/Engine/Source/Runtime/VulkanRHI/Private/VulkanBarriers.cpp#L1633) · [Zen submission history](../ZenCore/Source/Graphics/RenderCore/V2/RenderSubmissionHistory.cpp#L216)

### What removes first-use pipeline stalls?

ZenRHI and NVRHI create an initially empty, device-owned Vulkan pipeline cache. Leonida demonstrates importing compatible driver data on a subsequent run. UE5 handles two costs separately. The engine requests pipeline state object (PSO) compilation ahead of use, and the Vulkan backend can persist driver data in chunks keyed to the device. Driver-cache import can reduce the cost of creating a known pipeline. Precaching controls *when* creation happens. A draw can still wait if its pipeline was never requested in advance. [Zen cache](../ZenRHI/src/Vulkan/VulkanDevice.cpp#L581) · [NVRHI cache](https://github.com/NVIDIA-RTX/NVRHI/blob/bf0bbd9b666a7297492beb1999a4ddc0dfded143/src/vulkan/vulkan-device.cpp#L246) · [Leonida cache seed](https://github.com/ItsNotRexed/Leonida/blob/98fa503f8a19c3ed65df1f4f2f0e4571aa42c4f7/runtime/shims/d3d12_vulkan_device.cpp#L139) · [UE precache requests](https://github.com/EpicGames/UnrealEngine/blob/821fa3e7e3e5c66ddcd2d66d0603704f52e09fcc/Engine/Source/Runtime/RHI/Private/PipelineStateCache.cpp#L5011) · [UE chunked Vulkan cache](https://github.com/EpicGames/UnrealEngine/blob/821fa3e7e3e5c66ddcd2d66d0603704f52e09fcc/Engine/Source/Runtime/VulkanRHI/Private/VulkanChunkedPipelineCache.cpp#L155)

## Priorities for ZenRHI

1. **Close the validation acceptance gap.** A prior RTX 5080 probe hid the Khronos layer and the ZenEngine runner still reported success with zero validation errors. Leonida’s paired probe detected a deliberate write-after-write hazard and passed the corrected case. Use the same two controls through ZenRHI’s own instance and callback. [Zen acceptance runner](../tools/verify_rhi_production.py#L80) · [Leonida probe](https://github.com/ItsNotRexed/Leonida/blob/98fa503f8a19c3ed65df1f4f2f0e4571aa42c4f7/runtime/test/vk_sync_validation_selftest.cpp#L20)
2. **Measure cache reuse across ZenApp launches.** Keep file storage with the host and prototype optional cache-byte import/export in the backend. Compare empty and compatible seeds in fresh processes with identical renderer setup and driver conditions. Record pipeline creation time and the worst CPU frame on first entry into GI. Use UE’s precaching design for the remaining stalls attributable to late requests. [Zen pipeline investigation](RHIPipelineCompilationFollowup.md) · [Epic’s PSO precaching guide](https://dev.epicgames.com/documentation/en-us/unreal-engine/pso-precaching-for-unreal-engine)
3. **Measure CPU translation before adding workers.** Use a draw-heavy ZenApp setup and distinguish worker translation time from GPU waits and driver pipeline creation. If translation limits the frame, trial independent recording contexts while preserving submission order, completion serials, and failure handling. [Zen threading verification](RenderCoreRHIThreadingVerification.md) · [UE translation task dispatch](https://github.com/EpicGames/UnrealEngine/blob/821fa3e7e3e5c66ddcd2d66d0603704f52e09fcc/Engine/Source/Runtime/RHI/Private/RHICommandList.cpp#L800)

The NVRHI and UE5 comparisons are source inspections. Runtime evidence above comes from the earlier ZenEngine and Leonida validation probes. Performance rankings would require equivalent workloads and captures.

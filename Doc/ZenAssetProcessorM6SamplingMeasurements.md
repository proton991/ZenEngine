# M6 sampling and native texture allocation

24 October 2026. The expanded cooked-scene comparisons pass, including strong
minification and grazing views. The engine-native sampling test also passes with
16x anisotropy. Native array pages reduce image count but provide **no texture
allocation saving in these fixtures**. Arrays remain optional and off by default.

Environment: Windows, MSVC Release, NVIDIA GeForce RTX 5080, Vulkan Khronos
validation layer enabled. See the [runtime checkpoint](ZenAssetProcessorM6RuntimeVerification.md)
for upload/view ownership and the earlier source-absent package test.

## Cooked scenes

`EditorAssetRenderingTest` now covers both the original 16x16 material maps and
the 128x128 version generated by `generate_array_scene.py`. Both have five
instances, material variants, transformed UVs, color/normal/occlusion pairs, and
a standalone repeating alpha mask. Raw and BC7/BC5/BC4 packages use the normal
forced-recook v3 writer. Their temporary sources are deleted before package load.

Lighting is a fixed directional light with camera-light markers, environment
light and shadows disabled. This removes user camera-light settings and distance
attenuation from the comparison. The 16x16 fixture keeps front and oblique views;
the 128x128 fixture adds the following camera cases:

| Camera index | Orbit input, radians | Dolly input | Distance multiplier |
| --- | --- | ---: | ---: |
| 0 | 0, 0 | 0 | 1 |
| 1 | 0.65, 0.2 | 0 | 1 |
| 2 | 0, 0 | -6 | 2.46 |
| 3 | 0, 0 | -12 | 6.05 |
| 4 | 1.35, 0.2 | 0 | 1 |
| 5 | 0, 0 | -24 | 36.60 |

These are ordinary implicit-gradient material samples through the production
linear/trilinear samplers; the per-fragment LOD is not instrumented. Camera 5
leaves only a few covered pixels and checks extreme minification, not broad
material visibility. Every capture must contain colored pixels, and switching
the material variant must change the front view. The front and grazing captures
were visually inspected, as was the near-point-sized far capture.

**All 64 array-on/off frame pairs match exactly** at 256x192 across both profiles,
variants and inline/threaded execution: 12,582,912 RGBA channels. The saved PPM
comparison independently checks 9,437,184 RGB channels. This is within-profile
parity; it does not establish raw-versus-compressed image-quality acceptance.

The four tests pass in 6.911 seconds, with no Vulkan validation errors, zero
remaining VMA allocations at all four device teardowns, and no tracked CPU leaks.
Shader sources and SPIR-V hashes are unchanged across the run. Test duration is
recorded for reproduction and is not a processing or rendering benchmark.

## Native gradient and mip-tail samples

`ArraySceneTextureIntegrationTests.cpp` now samples each view at LODs 0, 0.75 and
2.5 (beyond the last level of the three-mip fixture), plus nine rotated-gradient
queries. Gradient major-axis lengths are 0.125, 0.5 and 2 in normalized texture
space; minor axes are one sixteenth of the major axes. Each is sampled at three
coordinates including the image edges. RGBA8 alpha alternates between 20 and 230
to exercise filtered alpha numerically.

The test compares production engine uploads of 5x7 RGBA8/BC7/BC4/BC5 pages with
standalone images, using both ordinary filtering and enabled anisotropy. The
recorded effective anisotropy is **16** in inline and threaded execution.
All **1,152 array/reference Vec4 pairs** (4,608 channels) and 288 alias pairs match
exactly. Counts include the two compatible view slots per layer; BC4/BC5 use the
same format in those slots. This is constructed engine-image data, distinct from
the cooked material scenes and the earlier standalone production-packer probe.
It does not exercise masked-material discard or GI/ray-query sampling.

All four native cases pass in 0.943 seconds with no validation errors, zero
remaining VMA bytes, and no tracked CPU leaks.

## Measured allocations

The cooked-scene fixture queries each unique live `VulkanTexture`'s
`VmaAllocationInfo::size`. Totals include the seven authored image resources or
their four packed replacements; they exclude the five runtime fallback images,
unused VMA pool blocks, descriptor/view storage, buffers, and driver overhead.
They are resource allocation sizes, not measurements of physical resident VRAM.
Inline and threaded results agree exactly.

| Map size/profile | Standalone allocation, bytes | Array allocation, bytes | Difference |
| --- | ---: | ---: | ---: |
| 16x16 / raw | 21,504 | 21,504 | 0 |
| 16x16 / BC | 18,432 | 18,432 | 0 |
| 128x128 / raw | 623,616 | 629,760 | +6,144 |
| 128x128 / BC | 211,968 | 216,064 | +4,096 |

Authored native images fall from seven to four. Texture binding slots stay at
twelve including fallback images, and the two authored sampler slots stay
unchanged. No draw-call, upload-time or frame-time benefit is claimed. These
results support leaving arrays opt-in until representative workloads demonstrate
a benefit; they do not establish a runtime profitability heuristic.

The subsequent [isolated upload measurements](ZenAssetProcessorM6UploadMeasurements.md)
compare matched 128/1024 raw/BC packages. They verify equal transferred bytes,
fewer copy regions, more native views and slightly larger allocations. Their
small GPU timing differences do not establish production asynchronous-upload
or frame-time benefit.

## Reproduction and evidence

Build `EditorAssetRenderingTest` and `VulkanRHIIntegrationTest` in the Release
integration build. Run the former with `ZEN_EDITOR_ARRAY_CAPTURE_DIR` set to an
existing output directory, and the latter with
`--gtest_filter=Execution/ArraySceneTextureIntegrationTest.*`.
Run `python ../ZenAssetProcessor/tools/validation/asset_processor_array_report.py <capture-directory>` to verify
all saved pairs, reconcile allocation totals and generate exact PNG transcodes.

Evidence under `build/asset-integration-release`:

- `m6-minification-build.log`, `m6-minification-tests.log` and `.xml`;
- `m6-minification-captures/`: 16 packages, 128 PPM captures and PNG transcodes,
  16 resource JSON files and `comparison.json`;
- `m6-minification-shader-identities.json`, `m6-sampling-allocation-identities.json`;
- `m6-array-gradient-build-2.log`, `m6-array-gradient-tests-2.log` and `.xml`.

M6 remains open for cooked array alpha materials, broader corpus/material and
ray-query/GI coverage, spatial filtering, and workload measurements of processing,
upload, binding/draw behavior and rendering costs. The failed spatial filtering
candidates and earlier allocation results remain documented; this checkpoint
does not weaken their visual threshold or replace the full acceptance gate.

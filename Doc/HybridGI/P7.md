# P7 hardware hard shadows

2026-10-11. Implements [P7](../HardwareRayQueryEnvironmentLightingPlan.md#p7-hardware-shadow-rays-optional). The receiver and voxel-injection CPU fixture gates pass on RTX 5080. **User decision: use hardware analytic shadows by default when supported (`voxel_gi_rt_shadows=true`), with shadow-map fallback.** This supersedes the initial opt-in decision. P8 still owns production-scene, platform and preset performance qualification. Machine-readable results are in [P7Verification.json](P7Verification.json).

## Behavior

**Hardware shadow rays** defaults to enabled in runtime and editor settings, including when `voxel_gi_rt_shadows` is omitted from `Data/engine.cfg`. Set it to `false` to request shadow maps. Mode 3, enabled shadows and a ready hardware GI provider are required. `auto` and `hardware` provider requests can use the feature; `voxel`, `legacy`, disabled RT, unsupported capability or failed/budget-rejected scene-query preparation retain shadow maps. The setting does not change the chosen GI provider or its budget.

Deferred, forward and scattering receivers issue one binary visibility query for each enabled shadow-casting light with nonzero incident radiance. Point and spot queries end at the light; directional queries extend through the scene bounds. Injection queries start at the reconstructed voxel-owner surface. Ownerless/degenerate voxels retain the existing voxel-visibility fallback. The deferred path uses the existing FP32 raster position; forward paths use interpolated world position and triangle-plane normals computed before divergent material branches. Deferred receivers share the same relative-degeneracy normal helper. There is no shadow temporal accumulation, filtering or soft-light sampling.

All queries reuse P4's full-scene TLAS, including triangles outside the voxel volume. Both triangle faces block. MASK candidates apply the material/vertex alpha, selected UV set, texture transform and sampler at mip zero; rejected candidates continue traversal. BLEND candidates apply the same test with a 0.5 coverage threshold. Transmission remains an opaque occluder under the existing query contract. Fragment ray hits explicitly sample their own UVs instead of the shaded fragment's UVs or derivatives. The scene-bound padding is clamped to the caller's finite endpoint, and point/spot endpoints are shortened by one float ULP.

Provider preparation now precedes shadow-map preparation. An active hardware-shadow frame records no map passes and releases retained map textures through the existing deferred resource release. Switching shadow settings or the resolved provider invalidates injection. A query-only frame that falls back before injection preserves pending cache invalidation; it cannot publish old radiance as current. Hardware injection uses the graphics queue, consistent with the other current hardware GI passes. Profiling and lighting metadata record both `rt_shadows_requested` and `hardware_shadows`; lighting metadata names the active analytic visibility method.

Editor preflight skips unused map memory when the current scene-query provider is ready and the proposed settings retain hardware shadows. Selecting map shadows, voxel/legacy providers, an insufficient acceleration-structure budget, or the shadow-map diagnostic still requires map preflight. Unavailable scene queries also retain map preflight; rendering rechecks allocation if provider preparation later falls back.

## Correctness evidence

Windows, NVIDIA RTX 5080, MSVC 19.51, Vulkan driver raw version `2588573696`. Debug correctness captures use synchronization validation. Release repeats of the seven static and two moving cases also pass. The demo, RenderCore tests, both native integration targets and editor UI build successfully.

The independent Embree oracle first passes its analytic self-tests. It traces the captured receiver positions against the generated glTF triangles and alpha masks. Expected direct lighting is the unshadowed capture multiplied by CPU binary visibility. Every meaningfully lit receiver must have the same lit/blocked classification; normalized RGB RMS must be below 0.1%. Injection independently reconstructs the captured owner positions and evaluates incident analytic light, CPU visibility and captured diffuse reflectance; its RMS limit is 0.2%, allowing the existing FP16 radiance storage.

## Initial cost comparison and adoption

MSVC Release `/O2`, RTX 5080, 960×540, 64³ compute voxels, owner reflectance, 1024² shadow-map faces, 16 warmup frames and 95 measured frames. Validation and VSync are disabled for timing. Both paths use hardware GI queries, one diffuse sample, cone bounce, disabled environment/emission/reflections and zero indirect intensity; the comparison changes only analytic visibility. Linear-light capture and profiling instrumentation are enabled on both paths. The fixture contains a floor and blocker (four triangles); moving runs animate the blocker and every point light at 60 Hz. Static maps/injection remain cached; moving runs rebuild their affected work.

Numbers below are complete **GPU frame elapsed milliseconds, median / P95**, not the sum of pass timings. This metric includes dependency waits and submission gaps and excludes screenshot readback and host presentation/compositor latency.

Moving-run injection medians (maps/rays) are 9.3/15.2, 22.7/18.6, 76.3/28.5 and 150.1/42.3 microseconds. Ray frames record no shadow-map passes. Shared TLAS update medians are approximately 24.2–24.8 microseconds. The JSON retains individual pass summaries, complete CPU/GPU frame distributions and cold-frame costs; cold GPU frames here are 70–75 ms and include shared initialization.

These measurements favor hardware shadows particularly with many moving lights, but a four-triangle fixture is favorable to ray traversal and does not establish foliage/large-scene cost. This single run does not establish a stable tail-time advantage on light workloads. The user subsequently selected hardware shadows as the supported-device default; shadow maps remain the compute-tier fallback and explicit opt-out. P8 must measure production scenes, multiple devices, memory peaks, actual issued rays and shipping presets for performance qualification and preset tuning. AMD hardware shadows and macOS/non-query hardware were not tested in P7; disabling RT on the RTX 5080 verifies the fallback mechanism only. Soft shadows remain out of scope.

## Reproduction

Use a Python environment with the dependencies required by `environment_reference.py` (NumPy, Pillow and Embree):

```powershell
python tools/validate_hardware_shadows.py --exe build/x64-windows-msvc-debug/bin/scene_renderer_demo.exe --output build/p7/final --allow-present-baseline
python tools/validate_hardware_shadows.py --exe build/x64-windows-msvc-performance/bin/scene_renderer_demo.exe --output build/p7/release --profile --allow-present-baseline
```

`--profile` disables validation/VSync and adds warmup only for the benchmark runs; correctness captures still use validation. The runner generates its glTF assets and CPU pose snapshots, retains linear captures and logs, hashes the executable and SPIR-V bundle, and restores `Data/engine.cfg` byte-for-byte. Raw data remain under the ignored `build/p7` directory; the checked-in JSON preserves the compact evidence and profile hashes.
